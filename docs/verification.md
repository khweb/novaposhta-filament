# Перевірка реалізації

## Реальне API та локальна черга відділень — 29.10.2026

- Виявлено й усунуто причину відсутності реального завантаження на `127.0.0.1:8824`: browser-router завжди підміняв HTTP fixtures. Звичайний режим тепер реальний, сценарії fixtures ізольовані. Стару локальну БД та зашифрований ключ збережено.
- Web і окремий PHP worker реально працюють з однією SQLite WAL-базою та файловим кешем. Реальна read-only перевірка збереженого користувачем ключа повернула `key_valid`; ключ і дані контрагентів не виводилися та не записувалися до журналу синхронізації.
- Перший реальний запуск №3 відхилено на сторінці 149 населених пунктів: два Ref перетиналися з попередньою сторінкою. Неповне покоління не опубліковано. Повторний повний запуск №4 пройшов цю межу та завантажив 26 771 унікальний населений пункт, 11 230 міст компанії й 5 типів відділень. Це спостереження за конкретним прогоном, а не гарантія незмінної пагінації API.
- Під час побудови нового покоління REST продовжував повертати старий довідник (`200`, один fixture-запис). Livewire polling реального звіту повертав `200`; у desktop не виявлено горизонтального переповнення. Браузер повідомив 404 для окремого ресурсу; відсутність усіх console errors не заявляється.
- Повний реальний запуск №4 опублікував **55 247** унікальних записів відділень/поштоматів. Тривалість — **790 секунд**, **628** запитів довідників; у цьому запуску немає помилок і повторів. Збережено 49 записів областей двох просторів, 556 районів і 9 720 явних пар CityRef/SettlementRef. Попередній невдалий запуск №3 залишається в історії та `failed_jobs`.
- У REST-перевірці знайдено помилку нормалізації: відділення №400 у Києві через `PostMachineType=FullDayService` потрапляло до поштоматів попри категорію `Branch`. Прибрано цю евристику, додано Ref поштоматів ПриватБанку; регресійні тести перевіряють обидва Ref, категорію та збереження payload відділення. Для застосування локальної корекції без повторних 628 HTTP-запитів скопійовано опубліковане покоління №4 у нове №5 та змінено класифікацію одного запису; публікація проходить штатну перевірку зв'язків.
- Покоління №5 успішно опубліковано штатною чергою після перевірки зв'язків, зовнішніх запитів для пересборки немає. Фінальний REST повертає `200`: **15 163** відділення/пункти та **40 084** поштомати. Для міста Києва (`SettlementRef=e718a680-4b33-11e4-ab6d-005056801329`) — **661** відділення та **7 397** поштоматів; відділення №400 знайдено у `type=branch`. Однойменне село Київ має інший Ref і не містить відділень: вибирати населений пункт лише за першою точною назвою неправильно. Worker перезапущено з актуальним кодом і залишено працювати; черга порожня, журнал stderr порожній.
- На PHP 8.4.27, Laravel 13.39.0, Filament 5.11.0, Livewire 4.4.8 та SQLite пройдено **71 тест, 527 тверджень**, Pint, Composer validate й PHP syntax (початкові 55 файлів, новий тест і змінений нормалізатор додатково). Нові тести перевіряють відновлення втраченої першої доставки, відсутність повторних запусків, незмінний дедлайн очікування worker та відмову без часткового запису за частково накладених сторінок.
- Поточні зміни не перевірялися повторно на MySQL/PostgreSQL, Laravel 12 або PHP 8.3. Наведена нижче історична матриця не є прогоном цих змін. Автоматичні тести залишаються з HTTP fixtures; реальний API перевіряється окремим локальним стендом.
- На початку граф доступний, перевірено покоління та coverage використаних шляхів. Coverage повертав `metadata_changed`; відповідні файли додатково прочитано безпосередньо. Фінальні пошук Tables і coverage нормалізатора/нового тесту повернули `Transport closed`; використано читання джерел, повнота графа не заявляється. Команди через початкову песочницю не запускалися через помилку її ініціалізації; для локальних перевірок використано дозволений запуск поза нею.
- Дослідження, джерела, експлуатаційні команди та обмеження — у [синхронізації відділень](warehouse-sync.md).

Перевірено повторну доставку, відкладене відновлення після `429`, `Retry-After`, вичерпання повторів, локальний ліміт без зовнішнього запиту, повтор сторінки між завданнями, відновлення втраченого dispatch, відкат записів разом із контрольною точкою та відкликання worker під час HTTP-запиту. Реальний database worker підтвердив публікацію успішного запуску, збереження старого покоління й безпечний запис остаточної помилки у `failed_jobs`.

Перевірено очищення журналу зі збереженням активних запусків і дати успіху, міграцію наявної бази без зміни зашифрованого ключа, різницю між відхиленням ключа й недоступністю перевірки, захист від пізньої відповіді для старого ключа, Gates та відсутність секретів у звіті.

Livewire-тести перевірили оновлення звіту під час роботи, фінальну подію, припинення polling після завершення, навігацію по журналу, призупинення стеження й авторизацію повторного запуску. Браузерний loopback-стенд перевірено у світлій/темній темі, на ширині 390 px та desktop: прогрес, подробиці, фокус клавіатури, відсутність переповнення звіту, стеження, справжній запит Livewire та `503 directory_not_ready` до першої публікації. Знайдене переповнення CSS grid виправлено. Браузерний стенд відтворює фіксовані стани; зміну етапів у часі перевірено автоматичним Livewire-тестом із фактичними кроками синхронізації.

Pint, Composer validate та PHP syntax пройдено. Нові перевірки використовують HTTP fixtures; реальний ключ користувача не надано й не перевірявся. MCP index_status та фінальний check_index_coverage повернули `Transport closed`: структуру перевірено читанням вихідного коду, повноту графа не заявлено. Застосовано правила локальних навичок Laravel/Filament/Livewire та доступності UI UX Pro Max; у локальній копії UI-навику є композиції таблиць і схем, але відсутня окрема reference record-detail.

Прогін MySQL виявив різницю affected_rows: оновлення heartbeat з тими самими значеннями може повернути 0. Виправлення перевіряє дійсний статус завдання замість припущення про кількість змінених рядків. Публікація також перевіряється із замороженим часом.

MySQL і PostgreSQL запускалися окремими процесами лише на loopback із новими data directory у tests/.databases. Наявні бази OSPanel не використовувалися. Тестовий bootstrap дозволяє db:wipe лише для явно вибраних баз nova_poshta_test*.

PHP syntax, Laravel Pint і composer validate --strict успішно перевірено перед постачанням. CI налаштовано додатково для PHP 8.3/8.4, Laravel 12/13, SQLite, MySQL 8.4 і PostgreSQL 17. Під час початкового етапу GitHub Actions ще не запускалися; результат після публікації наведено нижче.

Для захисту застарілих результатів перевірено встановлений Filament Select: результат застосовується лише за відповідного activeSearchId, відкритого dropdown та не знищеного компонента. Власну конкурентну JS-реалізацію не додано.

## Реальні публічні відповіді

Виконано успішні POST без ключа: getAreas, getSettlements, getCities, getWarehouses, getWarehouseTypes, searchSettlementStreets. Скорочені зразки — у tests/Fixtures. Підтверджено різні Ref областей компанії й територіальних областей, CityRef/SettlementRef і вкладені Addresses вулиць.

Повна реальна синхронізація всіх довідників не проводилася. Дійсний ключ користувача не надано: авторизовану перевірку Counterparty покрито fixture; реальну перевірку потрібно виконати в установленому застосунку явною дією на сторінці перевірки. Відомості контрагентів не зберігаються.

## Інструменти й обмеження

Прочитано локальні навички Laravel/Filament та офіційний Livewire 4. Відсутні SKILL.md і композиції UI підключено локально в .agents/skills без залежностей для користувачів пакета. Для UI UX Pro Max застосовано базові правила доступності й адаптивності разом зі стандартними компонентами Filament; окремий Python-пошук у каталозі рекомендацій не виконувався.

На початку сесії граф codebase-memory не містив вихідного коду: папка була порожньою. Після створення пакета під час оновлення графа MCP закрив транспорт; підсумковий check_index_coverage також повернув Transport closed. Завершення перевірено читанням джерел, PHP syntax, тестами й браузером; повнота оновленого графа не заявляється.

Покриття рядків не вимірювалося: активного Xdebug/PCOV немає. Локальна перевірка PHP 8.3 не виконувалася; після публікації PHP 8.3 успішно перевірено у GitHub Actions.

Після перевірок тимчасові сервери зупинено, їхні ізольовані data directory видалено. Браузерний стенд також зупинено.

## Інформативні довідники, фільтри та швидкий перегляд — 29.10.2026

- Усі п’ять довідників перенесено у дочірні пункти «Довідники» з лічильниками. Stack-рядки містять назву, застосовних батьків і Ref; лічильник таблиці відрізняє загальну кількість від результату пошуку/фільтрів. Типи відділень не мають пошуку, жоден довідник не має керування сортуванням.

- У п’яти таблицях працює штатний ViewAction із read-only infolist і Gate перегляду. Перевірено відкриття кожного типу запису та значення Ref, координат, батьків і локалізованого графіка роботи. Payload цілком у форму не заповнюється; відображаються лише вибрані поля.
- Повний PHPUnit на PHP 8.4.27, Laravel 13 і SQLite: **79 тестів, 850 тверджень**. Після фінального скорочення другорядних даних у вікні повторно пройдено PagesTest і DirectoryBrowserTest: **18 тестів, 444 твердження**. PHP syntax, Pint для змінених PHP-файлів і `git diff --check` пройдено. MySQL/PostgreSQL та іншу матрицю версій повторно не запускали.
- У браузері на 1440×1000 перевірено відсутність пошуку/сортування у типів відділень, інформативні рядки та модальні вікна. На 390×844 перевірено дочірні URL і лічильники мобільного меню, перегляд відділення та відсутність горизонтальної прокрутки. Кнопка «Переглянути» має висоту 44 px; Livewire-запити відкриття повертають 200, помилок і попереджень консолі немає.
- Штатний мобільний шаблон Filament 5.11 перевірено у вихідному коді: URL дочірніх пунктів береться з батька. Виправлений мінімальний Blade-шаблон застосовується лише до піднавігації пакета та використовує стандартні компоненти Filament без власного CSS.
- Застосовано базові правила UI UX Pro Max та доступні композиції Filament. Локальні `scripts/search.py`, `pro-rules.md` і композиція `record-detail.md` відсутні; результатів пошуку в базі рекомендацій не заявлено. Нові API-запити до Нової пошти чи синхронізацію для перевірки UI не запускали.
