# Синхронізація відділень і поштоматів

## Причина проблеми на локальному стенді — 29.10.2026

`tests/Browser/router.php` завжди викликав `fakeDirectories()`. Усі запити, включно з перевіркою збереженого ключа, отримували fixtures. Тому напис «Дійсний» та завершений запуск із одним відділенням не підтверджували зв'язок із Новою поштою. Сценарії `running` і `queued` додатково підміняли чергу. Збереження ключа саме собою ставить лише його перевірку, а не завантаження довідників.

Тепер звичайний запит до loopback-стенда використовує справжній HTTP Client, постійну SQLite-базу та database queue. Web і worker мають однакові налаштування БД та спільний файловий кеш для блокувань і лімітів. Збережений ключ і попереднє покоління залишаються в `tests/.databases/browser-completed.sqlite`; значення ключа не виводиться. Тестові сценарії доступні через заголовок `X-Nova-Poshta-Scenario: completed|running|queued|failed` і мають окремі `browser-fixture-*.sqlite`.

## Обраний підхід

Локальна проєкція довідника з версіями: пошук читає готову БД, а фоновий процес будує наступне покоління. Це застосування [Materialized View pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view): читачі продовжують використовувати останню повну версію, доки нову не перевірено й не опубліковано атомарно.

Для поточного API обрано повне завантаження. Надійного контракту інкрементальних змін і видалень у досліджених відповідях не підтверджено. Зокрема, не можна вважати зникле відділення видаленим після однієї сторінки чи оновлювати робочу таблицю через `truncate` перед завантаженням.

1. Єдиний запуск під спільним блокуванням; повторне натискання відкриває той самий звіт.
2. Завантаження областей, населених пунктів, міст компанії, типів і відділень. Ці залежності потрібні для коректного вибору відділення за населеним пунктом. `CityRef` і `SettlementRef` не взаємозамінні.
3. Одна сторінка — одне коротке завдання. Дані, лічильники, контрольна точка й ревізія фіксуються однією транзакцією. Повторна доставка старої ревізії нічого не змінює.
4. Перехід до порожньої сторінки, навіть після короткої. Перевірка дублів Ref, заявленої нижньої межі `totalCount` і граничного числа сторінок. `getSettlements` використовує Limit=150.
5. Перевірка адресних зв'язків і копіювання територіальних фільтрів до відділень. Часткові дані не публікуються.
6. Атомарне перемикання `active_generation_id`. Після збою залишається попередній довідник; наступний повний успішний snapshot також прибирає з активного пошуку відсутні записи.
7. Timeout HTTP, обмежені повтори `429`/`5xx`/мережевих збоїв, exponential backoff із jitter та врахуванням Retry-After. Такий підхід відповідає [рекомендаціям Amazon Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/). Очікування відбувається через відкладену чергу, звільняючи worker.
8. Спостереження за scheduler, worker, API та віком останньої публікації. Відновлення втраченої першої доставки й наступних кроків із тією ж ревізією; остаточний stale-запуск завершується помилкою. Повторна доставка queued-запуску не продовжує граничний строк очікування першого worker, що обчислюється від створення запуску.

Збереження ключа відокремлене від публічних довідників: підтверджені запити адресного API працюють без ключа. Ключ перевіряється лише read-only запитом Counterparty; дані контрагентів не зберігаються. Помилка ключа не повинна блокувати публічний довідник.

За замовчуванням автооновлення вимкнене; для робочого встановлення доцільний щоденний запуск о 03:00 Europe/Kyiv із ручним запуском за потреби. Частоту слід обирати за допустимим віком даних і фактичною тривалістю повної загрузки. Публічне API не надає підтвердженого snapshot token: атомарність нашої публікації не гарантує, що зовнішній довідник не змінився між його сторінками. За виявленої неповноти потрібен новий повний запуск.

## Запуск локального стенда

У двох терміналах із кореня репозиторію:

```shell
php -S 127.0.0.1:8824 tests/Browser/router.php
php tests/Browser/console.php work
```

Далі «Оновлення» → «Оновити зараз», або:

```shell
php tests/Browser/console.php sync
php tests/Browser/console.php status
```

`work` обробляє database queue й щохвилини виконує перевірку розкладу/відновлення. Без worker запит залишиться в черзі. Звичайні PHPUnit-тести продовжують блокувати мережу. Стенд має тестову авторизацію та тестовий ключ шифрування; він призначений лише для loopback і не є способом розгортання пакета. У встановленому Laravel-застосунку використовуйте стандартні scheduler і [queue worker](https://laravel.com/docs/12.x/queues), постійний APP_KEY та спільний кеш.

## Орієнтир розвитку

У [наведеному модулі OpenCart](https://ocmod.net/novaya-pochta-avtozapolnenie-goroda-i-podbor-otdelenij) описано автопошук міста, вибір відділення та поштомата, створення ТТН і відстеження. Його приватний код і спосіб синхронізації не досліджувалися; опис функцій не доводить внутрішню архітектуру.

Поточний етап — реальний довідник та залежний вибір населений пункт → відділення/поштомат через спільний PHP/REST-сервіс. Наступні окремі етапи: пошук за номером і короткою адресою, статус доступності/`DenyToSelect`, перевірка ваги та габаритів, інтеграція поля вибору у форму замовлення. ТТН, тарифи й трекінг потребують окремих вимог і не входять до цього виправлення.

Поштомат визначається за `CategoryOfWarehouse=Postomat` або налаштованим `TypeOfWarehouse`. `PostMachineType` не є такою ознакою: реальне київське відділення №400 із категорією `Branch` має значення `FullDayService`. Підтверджені Ref поштоматів — `f9316480-5f2d-425d-bc2c-ac7cd29decf0` та `95dc212d-479c-4ffb-a8ab-8c1b9073d0bc` (ПриватБанк). Для вже опублікованого довідника виправлення класифікації застосовується після наступної синхронізації; на локальному стенді створено окреме покоління з наявних payload без повторного мережевого завантаження та зі штатною перевіркою/публікацією.

Офіційний сайт [документації Нової пошти](https://developers.novaposhta.ua/documentation) повернув 403; контракти перевіряються прямими POST до офіційного `https://api.novaposhta.ua/v2.0/json/`. Числові результати реального прогону та обмеження записуються у [звіті перевірки](verification.md).

Перший реальний прогін зупинився на сторінці 149 населених пунктів: два Ref із назвою «Софіївка» вже були в попередній сторінці. Повторне читання межі повернуло інший набір останніх записів попередньої сторінки; другий повний запуск отримав усі 26 771 унікальні записи без дублювання. Джерело не гарантує незмінну версію між запитами: автоматично відкидати повторні Ref та публікувати отриманий залишок небезпечно. Зафіксована поведінка не доводить конкретного механізму кешування чи сортування на стороні НП. Поточна політика — безпечно відхилити неузгоджене покоління та повторити повний запуск.
